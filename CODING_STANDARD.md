# Coding Standard

🇹🇷 [Türkçe sürüm](CODING_STANDARD.tr.md)

This document defines the rules every line of airsonar code follows, and records every place where
the project knowingly departs from them. Each rule applied in the code is logged with its reason in the
[compliance log](docs/coding-rules/compliance-log.md).

## 1. Firmware (STM32, C++17)

### 1.1 Baseline

**[AUTOSAR C++14 Guidelines](https://www.autosar.org/)** — rules marked *required* are mandatory.

> **Verified edition:** rule IDs and wording in the compliance log are checked against **Release 17-10** of the document. The document is marked "AUTOSAR CONFIDENTIAL" and is therefore not added to the repository; only a link is given.

AUTOSAR C++14 is the main source of MISRA C++:2023. MISRA C++:2023 itself is a paid document and is not
used directly; the project therefore describes its code as *following the AUTOSAR C++14 guidelines*, not as
*MISRA compliant*. A formal compliance claim would require a full rule-by-rule check with a qualified tool.

### 1.2 Code ownership

| Folder | Owner | Rules |
|---|---|---|
| `App/` | This project | Full AUTOSAR C++14 + strict compiler flags |
| `Core/`, `Drivers/` | Generated by STM32CubeMX / vendor | Not checked (deviation D-001) |
| `USER CODE` blocks in `Core/Src/main.c` | This project | Kept to the minimum: one `#include` and one call to `app_main()` |

STM32CubeMX regenerates `Core/` and `Drivers/` and only preserves code between
`USER CODE BEGIN` and `USER CODE END`. All project logic lives in `App/`.

### 1.3 Language subset

- No exceptions (`-fno-exceptions`)
- No RTTI (`-fno-rtti`)
- No dynamic memory after initialization (`new`, `delete`, `malloc`, `std::vector`, `std::string`)
- Prefer `std::array`, `constexpr`, `enum class` and fixed-width integer types (`std::uint16_t`)
- Header files use include guards, not `#pragma once` (M16-2-3, A16-7-1)
- The preprocessor is used only for file inclusion and include guards (A16-0-1); no conditional declarations such as `#ifdef __cplusplus`
- No magic numbers: literal values get a named `constexpr` constant
- Data shared between interrupts and tasks must be documented and protected

### 1.4 Compiler flags

Applied to `App/` only (folder-level settings in STM32CubeIDE):

```
-std=c++17 -fno-exceptions -fno-rtti -fno-threadsafe-statics
-Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion -Wshadow -Werror
```

Generated code in `Core/` and `Drivers/` keeps the CubeIDE defaults, because vendor C code does not build
with these warnings enabled (D-001).

### 1.5 Verification

- Compiler warnings above, treated as errors
- `clang-tidy` with the configuration in [`.clang-tidy`](.clang-tidy)
- Manual review of every change against AUTOSAR C++14 for rules that tools cannot check
- Every rule applied or deviated from is recorded in the [compliance log](docs/coding-rules/compliance-log.md)

## 2. Host application (Qt) and DSP library

**Baseline:** [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/).
The shared `dsp/` library additionally follows the firmware language subset (1.3), because it also runs on the MCU.

## 3. Deviations

Every deviation from the baseline is recorded here with a justification.

| ID | Rule | Scope | Justification |
|---|---|---|---|
| D-001 | AUTOSAR C++14 (all) | `Core/`, `Drivers/` (STM32 HAL, CMSIS, CubeMX-generated code) | Vendor C code, regenerated by tools and not modified by this project |
| D-002 | C++14 baseline | Whole firmware | C++17 is used; C++17-only features are listed in the compliance log where used |
| D-003 | A5-2-2, M5-2-8 | Use of CubeMX/HAL macros (`*_Pin`, `*_GPIO_Port`, `GPIOx`) in `App/` | Vendor macros contain C-style casts and integer-to-pointer conversions. They are the only portable way to reach memory-mapped peripheral registers through the HAL. |
| D-004 | A18-1-1 (advisory) | String literal parameters of the form `char const (&)[N]` | A string literal is a C-style array; taking it by reference is the only way to get its length at compile time. Used only to convert literals into `std::array`. |

## 4. Rule identifiers

AUTOSAR C++14 rule IDs are used throughout the project:

- `Ax-y-z` — rules introduced by AUTOSAR
- `Mx-y-z` — rules inherited from MISRA C++:2008
